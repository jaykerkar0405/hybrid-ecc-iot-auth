Hybrid ECC authentication on two AWS t4g.nano "IoT" nodes

The protocol from hybrid-ecc-iot-auth ran between a device node and a server node on the smallest Graviton instances AWS sells. Both nodes had 2 vCPUs and 512 MiB of RAM, and they talked over a real VPC network. Every number below was measured on those nodes. None of it is simulated.

What was run

  1. Full test suite on the device node: 108 passed in 10.8 s, 97% coverage of protocol/ + crypto/. The 10,000-trial key-agreement property test took 5.0 s.
  2. Offline TA enrollment with hea-ta on the device node: one server and seven device identities, in 0.08 s and 25 MB RSS. The server credential was copied to the server node; the TA master secret never left the device node.
  3. hea-server on the server node, bound to 0.0.0.0:8443, plus a framed TCP echo server on :9000 for the network baseline.
  4. CLI walkthrough: a successful authentication, an adversarial replay, and cold-start timings.
  5. Handshake loops from one long-lived Device: 2,000 handshakes on both cores, then 1,000 pinned to one core with taskset -c 0. Each handshake opened a new TCP connection, as the CLI does.
  6. Security scenarios over the network: bit-flip tampering, the block-list, device restart, server restart, and a stolen credential.
  7. The repo's own paper-scale benchmark (bench.harness --full) on both nodes.

Server cost vs. enrolled-device population

Device nodeServer node

Mean handle_auth_request latency, 50 trials per point, probing the last-enrolled device. Source: bench.harness --full on each node.

Cost grows linearly at about 13 µs per enrolled device. Server.resolve_pseudonym scans every peer, and for each peer it hashes 8–25 candidate epochs to find the incoming pseudonym. At 1,800 devices one authentication costs 23.5–26.1 ms, so on compute alone a single-threaded t4g.nano server tops out at about 40 authentications per second, against about 13,000 per second with one peer. Both figures are compute-only ceilings from handle_auth_request time. The measured end-to-end rate with seven peers was about 1,300 handshakes per second, limited by the sequential client and TCP. The paper's per-operation model ignores this lookup, and it is the dominant server cost at IoT scale. An index from the expected next PID to its peer would make it O(1).

Findings

high

The device epoch lives only in memory, so a reboot locks the device out

Device._epoch is a plain dict (protocol/device.py) that is never saved to the credential store. Every new process starts at epoch 0. There were two failure modes on the testbed:

(a) Early restart. The server has already accepted epoch 0, so the next request gets ReplayDetected. The README's quick start works only because the second call is the replay demo. Running hea-device authenticate twice fails the second time.

(b) Restart after many sessions. The server's window is [last − 16, last + 8]. After 2,020 sessions, epoch 0 falls outside it, and all 1,020 retry attempts on the testbed got UnknownPeerError. Recovery depends on how the device retries. build_auth_request advances the epoch even on rejected attempts, so a long-lived process catches up after roughly as many rejections as it had accepted sessions: about 2,020 here, or about 5 s of back-to-back retries. The one-process-per-attempt CLI never catches up and stays locked out until the server restarts. Rejections of this kind never count toward the block-list. On a real deployment with months of sessions, a power-cycled node would have to send thousands to millions of rejected requests to get back in.

Fix: persist the per-peer epoch (write it before sending M1), or let the server resync with a time-based epoch.

high

hea-ta enroll gives every device every other device's long-term secret

TrustedAuthority.share_mutual_peer_keys distributes keys as a full mesh. device-001's credential therefore holds λ for all six other devices and for server-A. Since k*_ij = KDF(λ_device ‖ λ_server), anyone who extracts one device's file can derive any other device's pairwise key and pseudonyms. On the testbed, impersonate.py read only device-001.json and completed a full handshake as device-cli-05. server-A logged "outcome": "accepted", "peer_identity": "device-cli-05".

Fix: devices should receive only server λ values, and servers only device λ values. Each credential file also grows linearly with the mesh (836 B for 7 peers versus the 263 B the bench's storage model assumes for one peer).

medium

Block-list and replay window are lost on server restart

SessionLog is memory-only. device-tamper was blocked after three forged attempts, yet authenticated successfully after hea-server restarted. The replay window resets too. On the testbed, device-cli-01's M1 captured before the restart was rejected as a replay before it, and accepted after it. An M1 whose epoch is still within the new window (0–7 for a peer the server has not seen since restarting) can be replayed once. The attacker gets no usable session key, because that needs k*. But the server treats the stale request as a fresh authentication and advances that peer's epoch.

medium

Server lookup cost is O(devices × epoch window)

See the population chart above: about 13 µs per enrolled device, reaching 23.5 ms per authentication at 1,800 devices on a t4g.nano. The single-connection accept loop in hea-server means that cost directly limits throughput.

Comparing with the paper

The repo's benchmark summary reports a "99.9% processing reduction" (0.118 ms measured vs. 78.7 ms baseline mean). That comparison is not meaningful. The baseline values come from the paper's Table III constants for constrained embedded hardware (e.g. T_ECM = 17.1 ms, T_SE/D = 5.6 ms, T_H = 0.32 ms). Our figure is OpenSSL on an Arm core with dedicated AES and SHA-2 instructions. The repo's own methodology note says this too.

What this test does support: the online phase uses only symmetric operations (AES-256-GCM, HKDF-SHA256, SHA-256). That is why it costs about 0.1 ms of device CPU here and needs no elliptic-curve math per session. Communication is 182 B of raw protocol fields (352 B as JSON messages, 409 B of TCP payload with framing), against a paper-reported baseline mean of 301 B.

A t4g.nano still differs from a real IoT part. It has about 100× the RAM of a typical MCU, a 64-bit core at 2.5 GHz, and hardware crypto. On an 8/16-bit MCU without AES acceleration, expect device crypto one to three orders of magnitude slower. The shape of the results, with symmetric-only rounds and the server lookup dominating at scale, should carry over.
